## Executive Summary

The branch fixes most of what the phase 0 review asked for. Several of those fixes went too far or too short, and three of them make `new()` or `validate_request` behave worse than master. The most visible problem is that OAS30 now turns caller-argument errors into validation failures. Rewriting the remote-ref scan by schema position also broke it both ways: it misses `$defs` references reachable through a pointer, and it croaks on `x-` extensions under `paths`/`responses`. The highest-severity findings are security-related, see the security report. Every finding was confirmed by a probe or by reading HEAD code. Nothing was rejected as a false positive. After a pushback pass, pre-existing bugs are treated as in scope for this branch (0.012 is unreleased), so none is parked in the backlog.

### [I1] OAS30 `_catch_exception` turns caller-argument croaks and application exceptions into validation errors
- **File:** `lib/JSONSchema/Validator/OAS30.pm:92-97, 144-150, 196-204` (croak at `:410` in `_wrap_params`)
- **Bug:** Commit 3bdfd7e moved `_wrap_params` into `_validate_request` / `_validate_response`, and those now run inside the eval in `_catch_exception`. The eval catches every die, not only reference-load failures. The sibling `method` / `openapi_path` / `status` croaks still run outside the eval.
- **Impact:**
  - `validate_request(method => 'get', openapi_path => '/a', parameters => {query => [1]})` returns `(0, ['exception: param "query" must be hashref or coderef'], [])`. Master croaked.
  - A parameter getter that runs `die {code => 500}` returns `exception: HASH(0x...)`. The exception object is lost, and a memory address goes into a message that can reach the API client.
  - A programming error or a backend failure now looks like a bad request (a 4xx).
- **Suggested fix:**
  - Call `_wrap_params`, and any other argument-shape check, in the public methods before `_catch_exception`.
  - Catch only resolver/xget load failures, and rethrow a ref or object `$@`.
  - Add a test that a bad `parameters` type still croaks.
- **Confidence:** High
- **Found by:** Logic & Correctness, Contract & Integration, Error Handling & Edge Cases, Spec Compliance (`claude-opus-5-5`)

### [I2] The `new()` remote-ref scan misses references reachable only through a JSON pointer (regression from master)
- **File:** `lib/JSONSchema/Validator/URIResolver.pm:202-212` (`_check_remote_refs`)
- **Bug:** For Draft 4/6/7, adb1ff6 walks only `$SEARCH_ID` keyword positions. A `$ref` under `$defs`, or under any other non-keyword container, is skipped, even when a local `$ref` such as `#/$defs/a` points to it and validation resolves it.
- **Impact:**
  - `Draft7->new(schema => {'$defs' => {a => {'$ref' => 'http://example.invalid/s.json'}}, properties => {p => {'$ref' => '#/$defs/a'}}})` builds. Every validation then returns `exception: Remote fetching is disabled ...`.
  - Master croaked in `new()`. Changes, the `Validator.pm` POD and the `Draft4.pm` `fetch_remote` POD all promise the croak.
  - It still fails closed: nothing is fetched.
- **Suggested fix:** Follow local `$ref` targets during the scan, sharing `$seen`. If you don't, narrow Changes and POD to "references at schema positions". Add a `$defs` test either way.
- **Confidence:** High
- **Found by:** Contract & Integration, Spec Compliance (`claude-opus-5-5`)

### [I3] The OAS30 scan enters `x-` extension keys of Paths and Responses objects, so `new()` croaks on valid documents (regression)
- **File:** `lib/JSONSchema/Validator/URIResolver.pm:50-53` (`%OAS_NAME_MAPS`), `:204-206` (name-map branch walks `values %$value` with no `x-` filter)
- **Bug:** In OpenAPI 3.0, Paths, Responses and Callback objects can carry `^x-` extension keys next to their names. The name-map branch scans every value, including the extensions.
- **Impact:** `paths => {'x-ext' => {'$ref' => 'http://example.invalid/s.json'}}` croaks "Remote fetching is disabled". So does a `responses` `x-` key. Master builds both. This contradicts the comment at `:176-177` and the existing "x- extensions are data" test.
- **Suggested fix:** Skip `x-` keys in the `paths`, `responses` and `callbacks` name maps, but keep walking them under `properties` and `schemas`, where `x-foo` is a real name. Add tests.
- **Confidence:** High
- **Found by:** Spec Compliance (`claude-opus-5-5`)

- `lib/JSONSchema/Validator/Util.pm:375-417`: `canonical_json_key` / `_number_key` don't `local` the global Math::BigInt/BigFloat accuracy and precision. Under `Math::BigInt->accuracy(5)`, strict uniqueItems accepts `[9007199254740992, 2**53]`. The other number helpers in 4e5db03 localise them. Add the same `local(...)` (or put it in `_exact_number_string`), and add a uniqueItems case to the rounding subtest. (Concurrency & State, Spec Compliance)
- `lib/JSONSchema/Validator/URIResolver.pm:188`: `$seen->{refaddr $data}` ignores scope. A shared subschema reached under two `$id` scopes is checked only under the first, so whether `new()` croaks depends on hash order (3 of 6 runs croaked). Key on `"$scope\0" . refaddr $data`. (Concurrency & State, Logic & Correctness)
- `lib/JSONSchema/Validator/URIResolver.pm:88`: the `documents` key conflict check croaks when the entry is the same object (`schema => $root, documents => {<root $id> => $root}`), while the `$id` check at `:288-289` allows it. Master built this. Croak only when `$self->{cache}{$key} != $documents->{$document_uri}`. (Logic & Correctness, Contract & Integration)
- `lib/JSONSchema/Validator/URIResolver.pm:285-290`: `cache_id_dfs` keeps the trailing `#` on `$id`, but document keys go through `_document_key`. So an `$id` of `http://e.invalid/a.json#` in one document escapes the conflict check against a document keyed `a.json`, and `$ref a.json` and `$ref a.json#` resolve to different schemas. Normalise with `_document_key`. (Logic & Correctness)
- `lib/JSONSchema/Validator/OAS30.pm:197-203`: `_catch_exception` throws away the errors and warnings already collected. A deprecated op with a bad query parameter and a failing body `$ref` returns only the exception, with warnings `[]`. Create the context in the public method and append to it. (Error Handling)
- `lib/JSONSchema/Validator/URIResolver.pm:202-211`: the `new()` scan doesn't check OAS30 `discriminator.mapping` URIs, which the discriminator resolves at validation time. Check each mapping value in OAS30 mode, or name the exception in the POD. (Error Handling, Spec Compliance)
- `lib/JSONSchema/Validator/Util.pm:405-407`: a numified string such as `"5 "` gets a unique `canonical_json_key`, while `json_equal("5 ", 5)` is 1. Strict uniqueItems therefore accepts `["5 ", 5]`; only Perl-built data is affected. Key from `0+$n` when the regex fails. (Error Handling, Contract & Integration)
- `lib/JSONSchema/Validator/Util.pm:292-296`: `format_number` prints a BigFloat with |exponent| > 100 in exponent form (`1e+150`), while the same value as a BigInt prints in full. AGENTS.md treats message wording as stable. Add a Changes line, and consider a higher threshold. (Contract & Integration)
- `lib/JSONSchema/Validator/Util.pm:292-294`: `format_number` prints plain floats to 15 digits, so an exact bignum comparison reports "0.3 is equal or greater than 0.3" for `0.1+0.2` against BigFloat `0.3`. Format plain non-integers with `_exact_number_string`. (Error Handling)
- `Changes:27-28`: the example "9007199254740993 no longer matches 9007199254740992" already held on master. What changed is integer vs float, and only with `strict`. Reword it: "with strict ... no longer matches 9007199254740992.0". (Spec Compliance)
- `lib/JSONSchema/Validator/URIResolver.pm:164` (`cache_resolve`): pre-existing. A document loaded during validation is indexed without the conflict check, so its `$id` can silently replace a preloaded document or the root for the validator's lifetime: the first call is valid, the second invalid. The cache entry is also written before `cache_id`, so if `cache_id` dies, later calls see partial indexing that depends on hash order. Index into a temp hash and commit after success. (Concurrency & State)
- `lib/JSONSchema/Validator/OAS30.pm:52` (`validate_schema`): pre-existing. The scope is pushed and popped with no unwinding, so a die outside the per-keyword eval leaves one stale scope per call (count 2, 3, 4 on a reused validator). Pop on exception. (Error Handling)
